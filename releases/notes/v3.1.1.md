# Velaris v3.1.1 — The Update That Stopped Halfway

**Status:** PREPARED 2026-10-12 — final content; the release date is set when it is cut.
**Type:** Patch release — **contains a security fix**
**Upgrade from:** v3.0.0 or v3.1.0
**Migrations:** none

> **Why this exists.** On 2026-10-12 a real server's 3.0.0 → 3.1.0 update,
> approved in Studio, never ran — and when run by hand it stopped partway with
> the new code checked out and **none of its twelve migrations applied**. Three
> separate faults lined up. This release fixes all three and nothing else.
>
> **Nothing is removed or renamed, and an existing install keeps what it has** —
> including its MinIO container and every document in it.

---

## What went wrong

| # | Fault | Effect |
|---|---|---|
| 1 | **MinIO's images were withdrawn from Docker Hub** (around 2026-09-11; `minio/minio` and `minio/mc` both gone, and the pinned tags are not on quay.io). | The updater's image pull failed, and the script ended there **without a message and without recording a failure**. A new install could not be created at all. |
| 2 | **A stopped update looked finished.** The code pull had already moved the install to the new version, so the next run said "already on the channel version" and skipped the migrations for good. | New code on the old schema, permanently, with nothing saying so. |
| 3 | **"Update this environment" in Studio did nothing** on a server with no update agent. The button only records the approval; `velaris-update.timer` is what acts on it, and it exists only if somebody ran `update-velaris.sh --install-timer`. | The approval sat unread while the banner said it would apply "at the next agent check". |

## What changed

### The updater (`update-velaris.sh`)

- **A failed image pull is a warning, not the end.** An image the host already
  holds keeps working; one it truly lacks fails when the container is started,
  where it is named.
- **An update that stops says so.** Whatever ends the run after the backup has
  begun, the step it stopped at is printed and written to `.update-status`
  (`failed`), and Studio shows it.
- **Running it again finishes the job.** An interrupted update is recognised by
  a marker (`.update-in-progress`) or by migration files the database has not
  recorded, and is carried to the end instead of being reported as current.
  **The timer on its own never retries a stopped update** — a manual run or an
  approval in Studio does. That is the same rule a failed migration already had.

- **The timer-driven update finds its tools.** Run by systemd the script had a
  bare `PATH`, so `uv` (in `~/.local/bin`) was "not found" and the Python
  dependency sync was silently skipped. The script now looks there too, and a
  newly installed timer carries the installing shell's `PATH`.
- **No waiting for a passphrase nobody will type.** Without a terminal, git now
  fails at once instead of prompting. **If your install's git remote is SSH with
  a passphrase-protected key, the update agent cannot fetch** — the run is
  reported as stopped at "Pulling latest code". Use the HTTPS remote (the
  repository is public) or a key the agent can use.

### Document storage

- **A new install stores documents on local disk**, under
  `VELARIS_CASE_STORAGE_LOCAL_PATH`, encrypted with
  `VELARIS_CASE_STORAGE_MASTER_KEY` as before. **Put that folder in your backup.**
  It suits one server; more than one needs shared storage or S3.
- **Object storage is an endpoint you supply.** `VELARIS_CASE_STORAGE_BACKEND=s3`
  with `VELARIS_CASE_S3_ENDPOINT`, `_ACCESS_KEY`, `_SECRET_KEY`, `_BUCKET` and
  `_SECURE`. These are new names for the existing settings: **the
  `VELARIS_CASE_MINIO_*` names an install already has keep working**, and the S3
  name wins if both are set. No S3 server ships with Velaris any more, and a new
  install is given no MinIO setting at all. Tested against SeaweedFS 3.80 (put, get, exists, size,
  delete, missing-object handling, a 6 MB object, a non-ASCII key). `minio`
  remains an accepted value and means the same thing.
- **The bundled MinIO never worked on an install made by setup since
  2026-08-06 — fixed.** Setup wrote `STORAGE_BACKEND=minio` and a random password
  for the container, and never gave that password to the service, which signed
  with a built-in default and was refused (`SignatureDoesNotMatch`). Every
  document upload on such an install failed. The service now uses the
  container's password when no secret is configured and the endpoint is on the
  same machine. **On upgrade, uploads on such an install start working** — into
  the MinIO it was always configured for.
- **…and such an install is told the risk at every start.** The service logs
  `VEL-SYS-STORAGE-BUNDLED-MINIO`: the container's image can no longer be
  downloaded, so a host that loses it cannot serve its documents. The message
  names the two ways out (keep a copy of the image, or move to local disk).
- **An install that already runs the bundled MinIO keeps it.** The two MinIO
  services moved behind a compose profile, and
  `deploy/docker-compose/compose-profiles.sh` switches that profile on when the
  host already holds the `velaris-minio` container or its volume. Nobody has to
  set anything. `VELARIS_BUNDLED_MINIO=1` / `=0` overrides the detection.
- **A way off MinIO, if you want one:** `scripts/storage-migrate.py` copies a
  bucket to the local folder byte for byte, is safe to re-run, and has a
  `--verify` mode. It never deletes from the bucket, never edits `.env`, and
  prints the switch-over steps for you to take.

### Setup

- **A new install is offered the update agent.** Setup now asks whether to
  install `velaris-update.timer`, so that an update approved in Studio is
  actually applied. With `auto_update: false` (the default) the agent does
  nothing on its own. It is offered on a new install, or when a person is at
  the terminal — never on an unattended re-run over an existing install — and
  it warns if the git remote is SSH, which the agent cannot use with a
  passphrase-protected key.

### Studio

- **"PostgreSQL offline" in the sidebar now says what it means.** The label is
  the workflow engine's database link, not the database: it showed "offline" on
  a server that was serving data, because the engine had started without its
  database. It now reads "Engine database not connected", with the remedy
  (restart the engine) on hover.
- **The update banner says when the server has no update agent**, and names the
  two commands (`./update-velaris.sh --auto` now, or `--install-timer` once).
  Installing the timer remains the operator's decision.
- **The banner stays up after a stopped update** and shows why. It used to
  disappear, because the installed version already matched the channel's.

### Documentation

- **The install page showed a placeholder clone address** (`your-org/velaris`).
  It now gives the real HTTPS address. HTTPS matters here: an install cloned
  over SSH with a passphrase-protected key cannot be updated by the agent.

### Security

Found while checking this release's own changes, 2026-10-12:

- **A rollback request could run commands on the server.** `POST
  /platform/update/rollback` accepted any text as `to_version`, and the update
  agent put it into a `sed` expression — where GNU sed executes a command for a
  value carrying `/e`. It needed a platform operator's login and step-up
  authentication, so it turned a web administrator into a shell user rather than
  letting a stranger in. The API now refuses anything that is not a version
  (422), and the agent refuses it again before using it, for the channel
  manifest's version too.
- **The channel manifest was downloaded to a fixed name in `/tmp`.** Another
  local user could pre-create or swap that file and so choose the version
  installed. It is now a private temporary file, removed on exit.
- **S3 over plain HTTP is called out.** `VELARIS_CASE_S3_SECURE` defaults to
  false, which was right for a container on the same machine. With an endpoint
  on another machine the service now logs a SECURITY WARNING at start. The
  default itself is unchanged, because existing installs rely on it.
- **A new install's document folder is created private to the service user**
  (mode 700). A folder that already exists keeps its permissions.

- **Script scratch files left `/tmp`.** Error logs and the downloaded update
  package were written to fixed names under `/tmp`, where another local user
  could pre-create or redirect them. They now go to a folder only the install's
  user can write (`~/.local/state/velaris/`); messages print the new path. The
  service logs keep their documented `/tmp/velaris-<service>.log` names.

## What changes for an existing install

**Nothing, unless you act.** Specifically:

- `VELARIS_CASE_STORAGE_BACKEND` in your `.env` is not touched. An install on
  `minio` stays on `minio`, its container keeps running, and updates no longer
  try to pull an image that cannot be pulled.
- **One thing does change, and it is a repair:** if your `.env` says `minio`
  and document uploads have been failing, they will now succeed (see above).
  Check with `grep STORAGE_BACKEND .env` and by uploading a document.
- No setting is switched on. No migration runs.
- A rollback request whose `to_version` is not a plain version is now refused.
- If an earlier update left you half-updated, run `./update-velaris.sh` once by
  hand: it will find the unapplied migrations and finish.

**If your MinIO image is ever lost** (a pruned host, a restore onto a new
machine), it cannot be pulled again from the public registries. Either keep a
copy of the two images (`docker save`), or move to local disk with
`scripts/storage-migrate.py` while the container still runs.

## Upgrade notes

- **From v3.1.0 or v3.0.0 the update runs with your installed updater, which is
  the one with the fault.** It is expected to pass: the new compose file keeps
  MinIO out of the pull that used to fail. Should it stop anyway, run
  `./update-velaris.sh` again — the second run is this release's updater.
- **On a systemd install coming from v3.0.0**, run
  `deploy/systemd/refresh-after-update.sh` once afterwards (as for v3.1.0).
- `Velaris/.gitignore` and your own ignore rules: `.update-in-progress` is a
  runtime file, like `.update-status`.

## How it was tested — and what was not

- The updater's three changes were run in a harness with `docker`, `git` and
  `curl` replaced by stand-ins: a pull that fails; a stop at the migration step
  followed by a manual re-run; the timer alone meeting a stopped update; a box
  on the new version with unrecorded migrations and no marker; a healthy,
  current box, which must be left exactly as it is; a valid rollback; and three
  hostile version strings (two from the manifest, one from a rollback request),
  each refused with nothing executed. All ten behaved as described.
- The compose profile was checked on a host that holds the bundled MinIO
  (detected, services unchanged) and with the override off (MinIO absent from
  the service list and from the pull).
- The S3 backend and the copy tool were run against a SeaweedFS container, and
  the copied documents read back through the local store with the same key.
- The MinIO login failure was reproduced against a real bundled container, and
  the same service configuration then stored and read back a document.

**Not proven:** the updater has not yet completed a real 3.1.0 → 3.1.1 update
on a server, and no install has been created from scratch with this release.
Both are the first things to do with it.

## Not in this release

- A web-guided installer, a saved choices file and an install report — planned
  for v3.2.0.
- Any change to which S3 services are supported beyond "an S3-compatible
  endpoint"; only SeaweedFS was run.
- MySQL / MariaDB support in `update-velaris.sh` (still PostgreSQL-only).
