# Velaris v2.3.0 — Compliance, Evidence & Determinism

**Released:** 2026-08-04
**Type:** Minor release

> Closes the §8 compliance set — consent basis, personal-data discovery,
> double-entry books and disaster-recovery posture — and lands the platform
> determinism work behind it: an append-only case event stream, a CDC fan-out
> off the outbox, CRDT convergence for offline edits, and a Temporal
> interpreter that runs existing case definitions unchanged. Everything new is
> **off or additive by default**; the one behavioural change is that captured
> payments now post to the ledger.

## Compliance (§8)

**HxConsent** records *why* each use of a subject's data was lawful, at the
moment it became lawful. Append-only — a withdrawal is a new row, because an
overwritten row cannot answer "was this lawful **then**", which is the question
a regulator actually asks. All six GDPR Art. 6 bases are recorded, and a
withdrawal against a non-consent basis is refused: claiming processing stopped
when it lawfully continues would misstate the legal position. Purposes are a
closed vocabulary, so a typo is rejected at write time rather than silently
returning "no consent" forever. Portal submission records the basis as it
arises.

**HxPrivacy** scans every form and data model for probable personal data.
Customers build their own forms, so nobody could say from the schema where
personal data lived. A rescan **never overwrites a human verdict** — otherwise
every run re-opens every dismissal and reviewers stop trusting the list. Fields
that disappear are marked stale, not deleted: that personal data *was*
collected is itself a fact worth keeping.

**HxLedger** gives the platform balanced books. A transaction balances or it
does not exist; a mistake is corrected by a reversal, never an edit; money is
integer cents. Captured Stripe payments, refunds and confirmed disbursements
post automatically, and `/ledger/reconcile` reports money that moved without a
matching entry.

**Invoices deliberately stay out of the ledger.** Xero is the system of record
for invoicing, and posting accounts receivable here would be a second set of
books that can disagree with it. What was missing was the return leg: invoice
status only ever became `draft` or `failed`, so a paid invoice showed as a
draft forever. It is now refreshed from Xero when the case is read.

**HxDR** records the backups ops already takes and reports RPO/RTO posture per
region. It is a registry, not an executor. **A backup nobody has restored is
reported as `untested`, never as healthy** — reporting it green is precisely
the failure DR exists to prevent. A backup of a governed region stored
elsewhere is refused at record time.

**HxStatus** adds a public status page fed by a health sampler that had to be
built first: the health table existed and was empty, because its only writer
sat inside an endpoint nothing called on a schedule. The public payload is
built field-by-field from a whitelist — a subtractive filter starts leaking the
day someone adds a column — and it never claims uptime it did not measure.

## Platform determinism

- **Event sourcing for the Case aggregate** — an append-only stream beside the
  relational row, which stays the materialised projection so every read path is
  untouched. `GET /cases/{id}/events/verify` replays and compares, surfacing
  state written *around* the lifecycle chokepoints. Clean cutover at case
  birth, never a backfill. Off by default.
- **CDC event bus** — the outbox now fans out onto Redpanda (already running in
  compose and entirely unused), keyed by case id so one case's events stay
  ordered. A separate publish cursor keeps webhook semantics untouched. Off by
  default.
- **CRDT convergence** — an LWW-Register per variable on `(lamport, origin)`,
  not wall-clock last-write-wins, which offline clients cannot agree on.
  Converges whole values, not within a value.
- **Temporal `definition_json` interpreter** — one generic workflow reading the
  existing definition at runtime, so case-type owners need no migration. It
  contains no second copy of the process semantics. Opt-in twice.

## AI governance

- **LLMOps observability** — every call recorded at the one chokepoint they all
  pass through, **including failures**, since an error rate is half the point.
  Token counts are estimated from character length and the response says so.
- **`ai_action` step type** — the model proposes, a human accepts, edits or
  rejects. Even an auto-accepted action writes a row: an unattended AI write
  that leaves no trace is the one outcome nobody could defend.
- **GDPR Art. 22 provenance** — decisions now record the model that actually
  answered (not the configured default) plus a prompt SHA-256. The prompt
  itself is never stored.

## Also in this release

- **HxSandbox Phase 2 has a consumer** — HxSync WASM field transforms, which
  lifts the `runtime: wasm` install refusal. A failed transform fails the row
  rather than passing raw data through as if it had been transformed.
- **Smart Assignment** — `skill_based` and `manager_of` were selectable
  strategies that fell through to a log line. Both are now real.
- **Statistical SLA prediction** — percentile arithmetic, no model, works with
  AI off. Refuses below 50 samples rather than returning a confident-looking
  number.
- **Package format v2** — permissions as ReBAC tuples, restricted to relations
  HxGuard actually evaluates so a manifest cannot declare one that would never
  be satisfied. v1 stays frozen and keeps installing.
- **Rules migration report** — `GET /rules/lint/report` answers which case
  types can move to WASM defaults.
- **Error codes in responses** — stable codes reach the API body, the log line
  and now the UI, which links to the matching catalog entry. **Documents &
  Storage plus Authentication** (19 codes, 26 raise sites); other subsystems
  still return plain errors. No code distinguishes "no such user" from "wrong
  password" — that would be a user-enumeration oracle, and the omission is the
  design.
- **Frontend tests exist for the first time** — Vitest + React Testing Library
  + jsdom, with a `CI — Studio` workflow. This repository previously had no
  frontend runner, config or tests of any kind.
- **Scheduled PII scan** — the HxPrivacy inventory refreshes daily instead of
  whenever someone remembers, and confirmed personal data can be masked in
  exports that leave the tenant (off by default, never on the GDPR export).
- **At most one primary region** — `is_primary` was never reconciled across
  rows, so a deployment could hold two primaries or none.
- **Aggregate `/cases/{id}/detail`** — one request for what the case view needs.
- **Process mining moved off the OLTP pool** — it used the operations pool
  while a dedicated analytics pool already existed.

## Upgrading from v2.2.0

```bash
./update-velaris.sh
```

**One behavioural change:** captured payments and refunds now post to HxLedger
(`VELARIS_CASE_LEDGER_POSTING_ENABLED`, default on). It is additive — new rows
only, no existing payment path changes — but `/ledger/reconcile` will report
payments captured *before* this release as unmatched, because nothing recorded
them at the time. That is accurate rather than a defect; there is deliberately
no backfill, since inventing historical book entries is worse than an honest
gap.

Everything else new is off by default: event sourcing, the event bus, the
Temporal interpreter and HxSandbox all require explicit opt-in.

**If you run more than one region**, migration 152 demotes all but the oldest
primary and then enforces at most one. It promotes nothing — which region is
authoritative is a residency decision, not one a migration should make for you.
If no region is currently primary, HxDR cannot resolve one automatically; mark
one primary, or set `VELARIS_DR_REGION_ID`.

**Disbursements now post to the ledger when staff confirm the transfer**, not
when the disbursement is created — money that has not moved does not belong on
the books. Disbursements confirmed before this release were never posted, and
are not backfilled for the same reason payments are not.
