# Velaris v2.5.0 — Four Services, Three Databases, and a Platform That Says No

**Released:** 2026-08-26
**Type:** Minor release

> The platform stops being one process. Analytics, HxGraph and the migration
> domain each run on their own now, behind a gateway that is the only *caller*
> and not merely the only route. Two new modules ship — a people calendar and
> frozen HxDeploy promotion packages — and a great deal of this release is
> enforcement that was **described but not performed**: a package's declared
> permissions, a tenant's residency, a fraud detector that had never been asked
> a question. Those are listed as fixes rather than features, because that is
> what they are. Velaris also runs on **Kubernetes** now, on PostgreSQL, MySQL
> or MariaDB — optional, separate, and it changes nothing about the standard
> installation.

## The platform is four services

Analytics and process mining (`:8202`), HxGraph (`:8203`) and the migration
domain — HxMigrate, BPM importer, Scout, Orchestrator (`:8204`) — now run in
their own processes alongside case-service (`:8201`), all loopback-only behind
the gateway on `:8200`. **Client-facing prefixes are unchanged**; nothing an
integration calls has moved.

**The gateway is now the only caller, not just the only route.** Every service
binds `127.0.0.1`, which is a network boundary and not an identity: any other
process on the host could reach an authenticated API by opening a service port.
The gateway injects a credential and each service refuses a request without it.
Health, readiness and metrics stay exempt so supervisors and scrapes keep
working. It is **inert until configured**, so an upgrade cannot switch
enforcement on unattended.

**Internal mTLS ships built and off.** All four services talk over host loopback
behind a loopback-only gateway, so there is no wire to listen on; the certificate
authority, per-service certificates, rotation script and timer are in
`deploy/tls/` for the day a service moves to another host. The two layers are
independent: a caller holding a valid client certificate but no identity
credential is still refused. **Encryption is not authorization.**

**Ports are configuration.** Every port was a literal in three places at once, so
a client already using 8202 had no way to move it and no warning before the bind
failed. One table now names them, defaults unchanged, and **both the installer
and the updater check before anything binds** — the installer offers an
alternative, the updater halts before touching anything and never prompts,
because it runs unattended. The check answers three ways rather than two: free,
held by Velaris, or held by something else, **named**.

## Sign in with Google and GitHub

Two more identity providers on the login page, alongside SAML and Microsoft.
Provider marks are rendered monochrome so the login page can invert them in dark
mode without shipping four brand colours that fight the theme.

A related fix, because it made two shipped features invisible: Studio's sidebar
groups sections by **role name**, and the bot and scheduler pages were grouped
under a key no role matched. They were reachable by URL, present in search and
listed in the sitemap — and in no sidebar section, so nobody found them.

## Public URLs and firewall

An audit of what the platform tells the outside world about itself: only two
modules had ever known about `PUBLIC_BASE_URL`, so links generated elsewhere
could point at an address a customer cannot reach. Every service launch now runs
with `--proxy-headers`, so a request's real scheme and host survive the gateway
hop, and the workflow engine no longer binds `0.0.0.0` — on a server whose
firewall was not up, that was a public, unauthenticated port.

`setup-velaris.sh` gained an **opt-in firewall step**. It is a question and never
a default, and **ssh is allowed first**: enabling a firewall over an SSH session
with the wrong rules locks an operator out of their own server.

## People Calendar

Absence, availability and team meetings inside HxWork. The distinction the design
turns on: **leave is a fact, working hours are an assumption.** Leave alone
decides who can own work; leave *and* hours together answer "when shall we meet".
It fails open — an unreachable calendar never blocks an assignment — and a
colleague sees that you are busy, never why.

---

## HxDeploy — promotion packages

Frozen, sealed packages promoted between environments with selectable scope, now
covering bots and schedules as well as configuration. Promotion is gated by a
two-person rule, and the package is sealed at build time so what was reviewed is
what arrives.

---

## Bots — scheduler and definition editor

Bots are configured in Studio rather than by hand: a definition editor, a
schedule with fan-out, and a worker pool rather than a serial runner. A schedule
does not fire until somebody who is not its author approves it. Per-bot network
egress is allow-listed, and every attempt is recorded.

## Enforcement that was described but not performed

Four controls in this release existed as documentation, configuration screens or
unreachable code. Each is listed with what it now actually does.

### A package's declared permissions are a ceiling

A manifest v2 package declares what it needs as relationship tuples, validated
strictly at install — and the result was then **thrown away**. Nothing persisted
it and nothing read it, so a package could declare `viewer` on `report` and still
read every case its installing operator's grant exposed.

Two independent questions now, and a call needs both: the **grant** says what the
operator agreed to expose, the **manifest** says what the package may accept. The
manifest can only ever narrow. Enforced at the broker — the only data path a
package container has — and a package installed before this keeps working on its
grant alone.

### HxShield actually detects

The detection engine had eight patterns and **one caller**: an explicit scoring
endpoint. Nothing on a request path ever asked it anything, so a live deployment
held 3,905 recorded security events, two enabled rules and **zero incidents**.

Detection is now triggered by the platform's own security-event chokepoint, so
every call site that records an event gets scoring for free. Three call sites
that stayed silent — case creation, portal submission, form submission — now
record events. Off by default: eight rules that have never seen production
traffic are not switched on across a fleet by an upgrade.

Honest scope: three of the eight patterns are live. Two need events nothing
writes yet, two read context fields nothing computes, and one cannot work as
written. All eight are documented by name and reason rather than left to be
rediscovered.

### Rate limiting at the door

The gateway had **none**. What existed was in-process, reset on restart, and —
once the platform became four services — gave one attacker four buckets. Two
zones now, keyed on the peer address and deliberately not on a client-supplied
header, which would be a rate-limit bypass with extra steps. The anonymous
public portal is held tighter than the authenticated API.

### A policy grant reaches every service

Splitting the platform quietly broke policy propagation: the role→privilege
store loaded only in case-service, so a privilege granted **in data** worked on
some routes and silently not on others. One shared generation counter, bumped
inside the mutation's own transaction and polled every five seconds, now carries
grants *and* revocations to every process.

## Encryption

**Credentials move off hand-rolled cryptography.** The legacy format was not
broken — it authenticated what it stored — but it was cipher code written by
hand in a platform that already depends on a vetted AES-GCM implementation, and
it derived both its keystream and its authentication tag from one key. Every
synchronous caller now writes AES-256-GCM under a separately derived key. The old
format is still read and never written; a supplied script moves stored values
forward, verifying each one decrypts before replacing it.

**Secrets that belong to a tenant now use the tenant's key.** MFA secrets, SSO
client secrets, channel signing secrets, bot credentials, branch tokens and bank
references are stored under the per-tenant DEK where one can be resolved, so
erasing a tenant makes them unreadable. A bank reference is a data subject's
banking detail; that is the point.

**No configuration stores plaintext any more.** Marketplace tokens fell back to
plain base64 when no dedicated key was set — a personal access token readable by
anyone with the database, labelled as though it were a cipher.

**Adopting a master key is a script, not a setting.** With none configured the
key is derived from the platform's auth secret, so setting the variable changes
it and orphans every tenant key already wrapped under the old one. The supplied
tool re-wraps everything in a single transaction, verifying each key opens under
the new one before replacing the old.

## Security fixes

Named individually because each was reachable in a running deployment.

| Fix | What it was |
|---|---|
| **An empty secret killed the gateway** | An unset workload-identity secret rendered an nginx directive with no argument. nginx refuses to *start*, so an upgrade that changed nothing else would have taken the whole platform down. The empty case had never been run once. |
| **Token refresh downgraded a tenant's encryption** | A connector stored under the per-tenant key was silently rewritten under the platform key the first time its provider rotated a refresh token — Xero rotates on every use — and crypto-shredding that tenant stopped covering it. |
| **Marketplace tokens stored as base64** | With no dedicated key configured, personal access tokens were stored in plain text behind a `b64:` label. |
| **Certificate rotation reported success without restarting** | Rotation restarted only what systemd knew about, which is false both for "not installed" and for "running another way" — so it renewed certificates, skipped every live service in silence, and would have reported ✓. |
| **A hand-added secret vanished at boot** | On installs that render `.env` from a secrets vault, a value added by hand was lost at the next restart — silently taking its feature with it. |
| **Access-group changes did not reach other services** | Removing somebody from an access group left them working for up to 30 seconds platform-wide. |
| **Studio drifted to another port instead of failing** | When its port was busy, the dev server took the next one: the service unit said one number, the browser needed another, and nothing reported a problem. |
| **A detection producer copied form values** | Caught in review before release: submitted form answers would have been copied into security tables that no erasure request reaches. A fingerprint replaced them. |
| **Portal OTP had no throttle** | An anonymous six-digit code could be guessed 30 times in 0.1 s with no lockout, and the attempt counter was read-modify-write, so parallel guesses left the code alive. |
| **A public endpoint listed another tenant's case types** | By name, anonymously — and submission accepted them. |
| **Every bot's egress record was discarded** | The row keyed on a foreign key to the wrong grant table; the failure was swallowed at debug level after the access log had already been deleted. |
| **The superadmin boot gate was missing from the new services** | The service split carried 80 routes into three new processes and the gate was in none of them. Found by auditing what the split moved, not by a failing test. |
| **A credential lease displayed as two hours instead of three seconds** | Naive and aware timestamps compared without conversion. |
| **Product keys stayed "pending" forever** | The periodic verification endpoint returned a hardcoded `active` for any key that was not revoked, and never promoted the record. A working install was told it was active, wrote that into its own key cache, and heartbeated indefinitely while the dashboard showed it pending — with nothing to reconcile the two. The installer compounded it by writing "active" to that cache even when activation was unreachable or errored. *(Registration service — deploy separately from the platform.)* |

## Kubernetes, and three databases

Velaris can now be installed on Kubernetes, on **PostgreSQL, MySQL or MariaDB**.
Nothing about the standard `setup-velaris.sh` installation changes — the
Kubernetes scripts live in their own `K8/` directory, one per engine, and a
Docker install never touches them.

- `setup-velaris-k8s.sh` · `update-velaris-k8s.sh` · `stop-velaris-k8s.sh`
- **Reuse a database you already have.** Point an install at an existing
  Velaris database — an earlier install, a restored dump, a database outside the
  cluster — and the bundled one is not deployed. Before anything is written the
  target is inspected: empty is accepted, a Velaris database is adopted and only
  missing migrations applied, and **another application's database is refused**.
- **MySQL and MariaDB are first-class**, verified on 9.4/8.4 and 13.0/11.8.
  Service images need building with `--build-arg DB_EXTRAS="[mysql]"`; the
  driver is an optional extra by design.
- Ingress now supports **TLS** and controller annotations. Both default empty,
  so an existing install renders exactly as before.
- Pods now **drain before terminating** (`terminationDrainSeconds`, 5s), and an
  opt-in PodDisruptionBudget is available. Killing service pods under load on a
  multi-node cluster went from 0.11% of requests lost to 0.004%.

Measured on a capped 8 CPU / 16 GB cluster with two replicas per service:
PostgreSQL 387 rps, MariaDB 354, MySQL 350 at 40 concurrent users, with no
failed requests in any run.

## Fixes found while proving it

These are application defects, not Kubernetes ones. They affect every
installation, including Docker.

- **The API answered before it committed.** `get_session` commits in a FastAPI
  `yield` dependency, whose teardown runs *after* the response has been sent —
  so a client could create something, receive its id, and get a 404 fetching it.
  Measured on MySQL: 2 of 8 immediate read-after-write pairs failed, 10 of 12
  under load. PostgreSQL had the same race with a window too small to notice.
  Every request now commits between the handler and the response, and a failed
  commit surfaces as an error instead of a success reply over data that was
  never written.
- **Two migrations failed on every fresh install.** `051` reused an index name
  another migration had already taken, and `080` converted a column while its
  `NOT NULL` was still in place. Both are recorded as applied on existing
  installs, so this repairs new installs only.
- **`setup-velaris.sh` hid those failures.** Migrations ran through `psql`
  without `ON_ERROR_STOP`, so a file whose statements were rejected exited 0,
  was recorded as applied, and printed a tick. It now stops and says which file
  failed.
- **Analytics used PostgreSQL-only SQL** (`EXTRACT(epoch …)`), a hard 500 on any
  MySQL install.
- **Hard-deleting a case type that still had cases returned 500** instead of a
  409 naming the count.
- **`pyotp` and `prometheus_client` were imported but never declared**, so the
  built container images crashed on start.
- **The engine could never reach Temporal in Kubernetes** — it reads
  `TEMPORAL_HOST`, which the chart only set for the worker.
- **`/ready` answered 200 while reporting the database disconnected.** The
  endpoint runs a real query and puts `"status": "degraded"` in the body — but
  a readiness probe is decided by the status code, so a pod that could not
  reach its database stayed Ready and kept taking traffic. It now answers
  **503** when that check fails. Docker installs are unaffected in practice
  (nothing there probes `/ready`); on Kubernetes it is the difference between a
  rolling update stopping and rolling forward over broken pods.

## Re-verified from a cold start

The whole Kubernetes path was re-run on 2026-08-26 from nothing but the
repository — no cluster, no tooling installed. Three problems that had been
*written down* as known but never actually applied stopped a clean install
outright, and are now fixed:

- **The chart could not resolve its dependencies.** `valkey 4.0.2` no longer
  exists in the Bitnami repository, so `helm dependency update` failed and
  every engine died at the same step. Now pinned to `valkey 6.2.12` and
  `postgresql 18.8.13`. Note that Bitnami's 2025 policy leaves only `:latest`
  free, so the bundled database image itself is unpinned — pin
  `postgresql.image.tag` yourself, or use an external database.
- **`engine/Dockerfile` could not build**: `uv.lock` names `services/_shared`
  as a workspace member and the Dockerfile never copied it.
- **`VELARIS_IMAGE_REGISTRY` / `VELARIS_IMAGE_TAG` never reached helm.** Both
  are documented as the way to use your own registry or a pinned tag; both were
  used only to build and load, so the chart kept deploying its own
  `helix/*:latest` and the install sat in ImagePullBackOff. The update script
  re-pins images only when one of those variables is actually set, so
  `--reuse-values` keeps meaning what it says.

Also fixed: the worker was the one deployment with **no `imagePullPolicy`**, so
on the default `:latest` tag Kubernetes chose `Always` and it alone could never
start on a cluster with preloaded images; an ingress path that omitted the
chart-specific `service:` key rendered a backend named `<release>-helix-`; the
external-database helper pod was never deleted; and a failed `helm upgrade`
caused by a hand-run `kubectl set/edit/scale` printed the raw conflict with no
way forward — it now prints the command that hands the field back, which was
tested rather than guessed.

Two more, found by reading what the engine says at boot rather than watching it
go green — and both affect **every** installation, not only Kubernetes:

- **The engine was running on an in-memory store.** It reads plain
  `DATABASE_URL`; the chart set `VELARIS_ENGINE_DATABASE_URL`, which nothing in
  the codebase reads. It fell back to `localhost:5432`, was refused, and
  continued anyway — `database=in-memory`, health probe green, nothing said.
- **`velaris_sdk.protocols` could not be imported at all.** Ten of its
  re-exports named a class the module did not define, so the import raised
  `ImportError`; the engine catches that around its Temporal setup and ran with
  `temporal=unavailable` permanently. Both names now exist, so nothing that
  imports the old one changes. The engine connects to Temporal and registers
  its workflow and activities.

If you run on Docker rather than Kubernetes, the same two apply: check
`journalctl -u velaris-engine | grep -E "database_(connecting|unavailable)"` —
the host default happens to point at localhost, so it works only if your local
database really is the compiled-in one.

Result: **58/58 functional checks green on PostgreSQL 18.6, MySQL 9.4 and
MariaDB**, on a node capped at 8 CPU / 16 GB — clean installs, an install
pointed at an existing external database, and an uninstall-and-reinstall onto
the same volumes. TLS ingress, stop/start, adoption, refusal of a foreign
database, a deliberately failing migration and 4-byte UTF-8 round trips were
each exercised.

## Upgrade notes

- **Upgrade from:** v2.4.0
- **Migrations:** 164–174, verified on PostgreSQL, MySQL 8 and MariaDB 11.
- **Nothing new is switched on by upgrading.** Workload identity, internal mTLS
  and HxShield detection are all off until an operator turns them on. This is
  deliberate: enforcement that arrives unattended is enforcement nobody can
  diagnose at 3am.
- **Ports are unchanged** unless you change them. The defaults are exactly the
  values the platform has always used; the new variables only exist so a machine
  that already uses one of those numbers can move it.
- **The updater now halts instead of failing halfway.** It checks ports and
  required system packages *before* touching anything, and stops with the exact
  command to fix it. It never prompts and never chooses a port for you.
- **If you run a secrets vault**, push new settings through it rather than
  editing `.env` — the file is re-rendered at boot, and the renderer now refuses
  a render that would drop a key the file already holds.
- **Studio now fails to start if its port is taken**, rather than quietly moving
  to another one. If Studio does not come up after this upgrade, that is what to
  check first.
- **No new feature keys in the release manifest.** Every capability here is
  switched on by its own configuration or environment switch; a manifest row on
  top would be a second switch that can disagree with the first.
