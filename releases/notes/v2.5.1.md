# Velaris v2.5.1 — Bring Your Own Calendar

**Released:** 2026-08-27
**Type:** Patch release

> One feature and two fixes, all in the same corner of the platform. The
> calendar can now read the calendar people already use — uploaded as a file,
> or subscribed to by address and re-read on a timetable — and hand yours back
> as an `.ics`. The fixes are to internal certificate rotation, and both were
> latent: they would have fired for the first time on the day rotation finally
> had something to do.

## Bring your Outlook, Google or Apple calendar with you

The calendar's consumers are only as good as what is in it. Assignment and
escalation route work by who is available, and the resolver **fails open** — so
if a team keeps its leave in Outlook, Velaris sees an empty calendar and
cheerfully hands work to somebody on holiday. Three ways to close that:

- **Upload an `.ics` export** — a one-off snapshot. It previews first: what would
  be added, what updated, what leave requested, and every entry it could not take
  with the reason. The second click confirms something you have read.
- **Subscribe to a calendar's address** — the same reader on a URL, re-read on a
  timetable. This is "add a calendar by URL" as Google and Outlook offer it, and
  like theirs it is **read-only**: Velaris reads that calendar and never writes
  back to it.
- **Export yours** as `.ics` over any date range, to open in Outlook, Google or
  Apple Calendar.

All three live on a new **Import / Sync** tab in Calendar.

**Out-of-office arrives as a leave *request*, never as approved leave.** Only
approved leave reroutes a team's work, and a file should not be able to empty
somebody's queue. For the same reason a feed can cancel an entry that has left
it, but **never touches leave a human has approved**.

**Subscriptions are off until an administrator says where from.** Fetching a URL
a user chose is the shape of every SSRF, so this server only reaches hosts named
in `VELARIS_CASE_CALENDAR_FEED_HOSTS` — unset means no subscription can be
created at all, which is exactly how an existing install behaves today. The
resolved address is checked as well as the name, redirects are refused rather
than followed, and the size cap is enforced while the response streams.

Treat a subscription address like a password: a Google or Outlook private link
has a token in it, so Velaris shows it back only to the owner, their manager and
an administrator.

A calendar that has been failing for a fortnight **says so**, with the reason and
when it last worked. A sync that silently stops is worse than one that never
started, because the calendar still looks full.

What you can export is what you can see: somebody else's private meeting is
**not in the file at all**, and the reason for their leave is reduced to "Away"
unless you are the person, their manager or an administrator. An export leaves
the platform, so the filter is at least as strict there as on a screen.

Two-way sync with Exchange or Google — where a change here appears there — is
deliberately **not** built: that needs a signed-in connection to your mail
provider and raises the question of which side wins when both change.

## Every screen has the same tabs now

Studio had **four tab styles at once** — an underlined bar, an UPPERCASE
monospace version of it, a pill on a card, and a segmented button group — because
each module copied whatever its neighbour did on the day it was written. Every
tab bar in the product now comes from one component, with the Help Centre's
geometry as the reference.

It is not only the labels. A module's bar used to sit inside the page's own
padding, which pushed it away from the header above it and stopped the underline
reaching either edge. The bar is now flush under the header on every screen, and
the page padding applies to the content beneath it.

Two things this turned up, now fixed: **HxNexus showed "BPM Translator" twice** —
one of its tabs had no label of its own and fell through to its neighbour's — and
**Risk Review printed its own title** below the one the page header already
showed.

## "Customer Portal" is now "Portals Management"

The staff screen at `/portal-admin` was called *Customer Portal*, which is also
the name of the public site your customers actually use. The staff screen is
**Portals Management**; the customer-facing portal keeps its name. Nothing moved
— same route, same permissions, same features.

## Fixes

### Certificate rotation renewed, then could not restart anything

`velaris-cert-rotate.service` ran as the Velaris user, contradicting its own
documentation. Renewing certificates works as any user; **restarting the services
afterwards does not** — that needs privilege. A rotation would therefore have
replaced all five certificates and then left four services running on the old,
now-expired key material, reporting the failure to the journal and nowhere else.

Nothing had noticed because nothing had been due: the timer had printed "nothing
due" every day since it was installed. It fires for real the first time a
certificate reaches 21 days from expiry.

The unit now runs as root, and the rotation script hands the renewed files back
to whoever owns the certificate directory — the services do not run as root and
could not read a root-owned key they had just been given.

**If you installed the rotation timer before this release, re-run
`sudo deploy/tls/install-rotation-timer.sh`.** It rewrites the unit; nothing else
changes and the certificates are not touched.

### A machine that was off across an expiry came back broken

Certificates that lapse while a machine is switched off *are* replaced — the
timer treats "expired" as inside its renewal window, and it catches up on the
firing it missed. But it does so up to thirty minutes after boot, and until then
every internal handshake fails: with internal TLS on, the whole platform is down
and the only symptom is that nothing can reach anything.

Services now check before they start. If internal TLS is on and the certificate
has **already expired**, it is renewed first and then the service comes up. Start
time is the easiest place for this — nothing is running yet, so there is no
restart to perform and no privilege needed for one.

Deliberately narrow: only an already-expired certificate triggers it, so an
ordinary restart during the renewal window does not mint a new key; it runs under
a lock, because four services starting at once would otherwise renew
simultaneously and race on the shared certificate authority; and a renewal that
fails never blocks the boot.

**With internal TLS off — the default — none of this runs**, and the command line
every service starts with is unchanged.

## Upgrade notes

- **Upgrade from:** v2.5.0
- **Migrations:** 175 and 176, verified on PostgreSQL, MySQL 8.4 and MariaDB 11.8.
  Both are additive: new columns and one new table, nothing renamed or removed.
- **Nothing new is switched on by upgrading.** Calendar subscriptions cannot even
  be created until `VELARIS_CASE_CALENDAR_FEED_HOSTS` names a host, and importing
  and exporting are actions somebody takes, not behaviour that starts on its own.
- **A subscribed calendar only refreshes if something asks it to.** Nothing polls
  on its own: create a `calendar_feed` schedule in the Scheduler. Running it every
  fifteen minutes is fine — each calendar is still only fetched when its own
  refresh interval is due. Without a schedule, a subscription updates when
  somebody presses Refresh and not before.
- **Re-run `sudo deploy/tls/install-rotation-timer.sh`** if you installed the
  rotation timer on an earlier version. Only relevant if you turned internal TLS
  on; if you did not, there is nothing to do.
- **No new feature keys in the release manifest.** The calendar work is switched
  on by its own configuration, in keeping with v2.5.0.
