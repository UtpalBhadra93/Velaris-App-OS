# Velaris v3.1.0 — The Tenant Boundary, The Rep Desk, and Legal Holds

**Status:** PREPARED 2026-10-11 — final content; the release date is set when it is cut.
**Type:** Minor release
**Upgrade from:** v3.0.0
**Migrations:** 206–217 (PostgreSQL, MySQL 8.4, MariaDB 11.8; 217 is PostgreSQL-only)

> **Why this is a minor.** No route, setting, column or script flag is removed
> or renamed. Every new feature is additive and ships **off, or unused until
> somebody uses it**: a legal hold exists only once one is placed, a staged
> rollout only when a deployment asks for one, and each new switch is off
> unless set.
>
> **What does change on upgrade is who may do what — and only on a
> multi-tenant install.** October was mostly a security month. A sweep of every
> route found that a non-default tenant's administrator could read, change and
> in places delete another tenant's records, and could use platform-wide
> screens. Those doors are closed. **A single-tenant install sees no change**:
> its administrators are the default tenant, which is the platform operator.
> **Read §What changes for an existing install before upgrading a multi-tenant
> one.**
>
> **What is not in this release** is listed at the end, under *Not in this
> release*, rather than implied.

## Legal holds

A case under a legal hold can still be worked. What it cannot be is destroyed,
anonymized, erased or moved until the hold is released.

- **Place** a hold on a case with a matter reference and a reason (admin or
  security officer). **Release** it with a reason (admin only). A case takes one
  active hold at a time; a released case can be held again.
- **What a hold freezes**, each at the place it happens: retention (delete,
  anonymize, audit and event pruning), the `delete` action, deleting documents,
  document versions, time entries, AI conversations and canvas boards on the
  case, customer erasure (from the portal, by an administrator, from the rep
  desk), staff-user anonymization, moving the case to another tenant, permanent
  tenant deletion and key shredding.
- **Who sees what:** anyone who can read the case is told *that* it is held. The
  matter and the reason are read by admin and security only.
- A customer's own erasure request on a held case is refused without saying why,
  and is not lost: it is recorded as a pending request for staff.
- Holds are never deleted. A released hold is the record that the freeze existed
  and who lifted it.
- **In Studio:** a banner and a *Legal hold* tab on the case; *Compliance → Legal
  Holds* lists every hold and releases by matter.
- Migration **215**. No hold placed means nothing is frozen — exactly as before.

**Not built:** a two-person rule on release, expiry or review reminders,
custodian notices. Raw database access is not prevented.

## Staged rollout of content

A new version of a case type no longer has to replace the old one at once. The
strategy is chosen **per deployment**, when a package is promoted, and the target
environment's operator approves or overrides it.

| Strategy | What it means |
|---|---|
| **Immediate** (default) | Active for all new cases at once. Today's behaviour, and what an older package gets. |
| **Feature flag** | Installed but dormant until an operator activates it. |
| **Percentage** | A sticky share of customers get the new version for new cases; raise it step by step, on a schedule if you like, with a guard that holds or rolls back. |
| **Blue-green** | Both installed; one switch moves everyone, and switching back is the rollback. |
| **Shadow** | The new version is evaluated alongside with no effect. |
| **A/B** | A percentage rollout plus an outcome comparison per arm. |

- Cases already running stay on the version they started on. A rollout only
  chooses the version for **new** cases.
- One open rollout per case type: a second is refused, and the refusal offers
  finish, roll back or supersede.
- Pilot targeting, version status (retired / withdrawn), a rebase tool for safe
  cases after a rollback, and webhook events for every change.
- Migrations **210–211**. Privileges `content.rollouts.*`. Studio: *HxDeploy →
  Rollouts*, and a strategy dropdown on Promote.

**By design:** only case types roll out; rules, processes and forms go out
inside a case type version. Percentages are statistical, not exact. While a
rollout is open, an immediate import of that case type is refused.

## Rep desk

The rep desk gained the rest of what a rep needs without leaving the screen.
It remains gated twice — released by the platform and entitled per tenant — and
is dark until both are true.

- **Bring in a colleague** — a single-use, short-lived link that brings a second
  named rep into the same live contact, warm or cold. The customer is not
  re-verified. Migration **207**.
- **The full action rail** — reply on the customer's channel, send a document
  request or a checkout link, book a callback, start a live session, capture or
  withdraw consent. Each action asks the consent ledger first and is **disabled
  with the reason** when it may not be used. Nothing is shown that the call's
  verification tier withholds.
- **Profile backfill** — an operator action that *proposes* customer profiles
  from history (portal customers, case submitters). It never creates or merges on
  its own. Migration **208**.
- **Related people** — suggestions from shared evidence (a shared caller number,
  a shared case, a shared non-webmail domain), shown as suggestions. One click
  confirms a relationship; it never grants authority to act for someone.
- **Industry rail packs** — a rail is now configuration a marketplace pack can
  carry. Three official packs: banking dispute, telco port-out, clinic booking.
  Migration **209**.
- **Erasure reaches the rep desk** — erasing a customer now removes their rep-desk
  profile too, from every erase path.

## Customer data export (GDPR Art. 15)

One export of everything held about a customer: account, rep-desk profiles,
cases, shared messages, documents (listed), orders, conversations, SMS, emails,
calls, relations and consent — for the caller's tenant only.

- **Staff:** `POST /enterprise/gdpr/customer-export`, with a reason, recorded as
  a GDPR request. Internal notes and agent identities are withheld unless the
  operator opts in; credentials, one-time-code hashes and raw payloads always
  are. The export names what it does not include.
- **The customer:** *Download my data* in the portal, their own account only,
  rate-limited.

## Tenant-owned design content

Until now a case type, form, rule, data model or business calendar with no
tenant was everybody's, and one tenant's import could overwrite another's.

- A new one belongs to the tenant that creates it. A shared one is created only
  by the platform operator, deliberately, as a **default**.
- **Defaults are inherited, copy-on-write.** Every tenant reads the default. A
  tenant that edits it gets its own copy, which wins for that tenant from then
  on, and is never overwritten. When the default changes later the copy shows
  *Update available*.
- Uniqueness is per tenant: two tenants may each have a case type of the same
  name and version.
- Eight record tables (artifact branches, commits, app packages, GDPR requests,
  notification logs, import jobs, migration scans/projects/tasks) gained an
  owner; existing rows are the default tenant's.
- Migrations **212–214**. Existing rows keep working unchanged; an operator
  screen proposes moving a default to the one tenant that uses it, and moves
  only what the operator applies.
- **In Studio:** a *Default / Your copy / Update available* marker on case types,
  forms, rules and calendars.

**Not built:** merging a copy back onto its changed default; escalation trees,
notification overrides, email templates, webhooks and intake events are not
copied into a tenant's copy and keep pointing at the default.

## Moving a case between tenants

- A **Move tenant** tab on the case, shown only to someone the server allows,
  with a **preflight** that lists the blockers before the button; and a
  *Case transfers* page for outgoing and incoming requests.
- A case with channel history can now be moved. Conversations and email stay
  with the source, detached and closed; the destination gets a read-only
  transcript with staff names pseudonymised.

## Field operations — the node

The device half of offline field operations: one SQLite file and a signing key
(`python -m velaris_shared.field_node`, profile in `deploy/field-node/`).

- Fails closed once its bundle is stale; a clock set back is refused; exports
  are denied offline by default; synced data is dropped from the device.
- The hub now delivers a shred order on **every** contact, not only on a
  successful sync — a refused sync used to leave the data on the device.
- `VELARIS_FIELD_REQUIRE_SIGNATURE` (off by default, as released) refuses
  unsigned syncs and contacts.

**Not proven:** two physical devices, or a real 72 hours offline.

## Documents and Q&A

- **Background indexing on upload** — `background=true` queues the upload and
  returns at once. Unset, it is indexed in the request exactly as before.
  Migration **206**.
- **Structure-aware chunking** (`VELARIS_CASE_HXNEXUS_CHUNK_STRATEGY=structure`) cuts on headings,
  paragraphs and sentences and keeps the heading with each chunk.
- **Rerank** (`VELARIS_CASE_HXNEXUS_RERANK`) blends similarity with a keyword score over a
  wider candidate set. Local arithmetic — no model call, nothing leaves the box.
- Both are off unless set; an unknown value is off, never an error. Existing
  chunks keep working; re-cutting is the existing re-index action.

**Not measured:** there is no before/after benchmark on real long documents.
The keyword score has no stemming.

## Privacy — three more surfaces

Each has its own switch, each is **off unless set**, and none is implied by the
existing export-redaction switch.

| Switch | What it does |
|---|---|
| `VELARIS_CASE_PII_REDACT_TABLE_EXPORTS` | Database Manager table exports mask confirmed personal fields, inside JSON columns too. |
| `VELARIS_CASE_PII_MASK_AI_EGRESS` | The values of a case's confirmed personal fields are masked wherever they appear in text sent to an **external** AI provider, and restored in the answer. |
| `VELARIS_CASE_RETENTION_ANONYMIZE_CASE_TEXT` | Retention's anonymize also blanks the case's messages, channel messages and AI conversation text. Irreversible, hence opt-in. |

## Security fixes

All found by the project's own audits, each proven before it was fixed.

- **Script tasks ran arbitrary Python.** A process script is now assignment
  lines over a checked expression language; `exec` is gone. Refused at create,
  update, validation, import and run time. `GET /fusion/definitions/script-scan`
  lists any stored process that would now be refused. Marketplace packs carrying
  one are refused whole.
- **Payments had authentication and nothing else.** A caller in one tenant could
  record a disbursement on another tenant's case; a viewer could disburse. Seven
  `payments.*` privileges; every route checks the case.
- **Every route keyed by an id, and every list.** A permanent probe seeds one
  row per table for one tenant and calls every route of all four services as
  another. It found about 110 id routes and 45 lists crossing tenants — among
  them deleting another tenant, its SSO providers and audit-stream targets,
  running its connectors, and reading every table raw through the Database
  Manager. One app-wide guard now maps each id to its owner; another tenant's
  row is a 404. Ids in a request body or query string, MCP tool arguments and
  realtime subscriptions are checked the same way.
- **Self-promotion to superadmin.** The user-edit and register routes took
  `roles` as sent. Only a superadmin grants superadmin now, and an account a
  tenant's admin creates joins that tenant.
- **Outbound webhooks.** A viewer could subscribe to every tenant's case events,
  and the test route would post to any address. Privileges added; a platform-wide
  subscription is the operator's alone; the address check runs on create, change
  and test.
- **Portal administration** trusted the tenant named in the URL.
- **Login-only routes.** A scan found 270 routes gated by a login alone; 101 are
  now gated by 22 new privileges, and the 169 left are listed with a reason in a
  test that fails the build when a new one appears.
- **Tenant taken from input, or not recorded.** A sync run exported every
  tenant's cases to any destination; a tenant admin's SCIM token was stored with
  no tenant; cases created by several paths were stored with no owner.
- **Compliance evidence packs** named another tenant's administrators and counted
  its audit actions; a tenant could list and download another's report. A pack
  is now built from the caller's tenant only.
- **Marketplace sources** and **app snapshots of the whole install** are the
  platform operator's.

## Fixes

- **Audit chain and retention.** A retention policy on the audit log deleted
  rows the chain had sealed, and verification then reported tampering — for
  good. The purge now seals a *prune record* into the chain naming the rows it
  removed, and verification counts them as pruned and passes. A row removed
  without one is still a break. Migration **216**. *Purges made before this
  release left no record, and still verify as missing.*
- **Feature flags on an older install.** On an install first set up before
  v2.5, migration 080 could fail and still be recorded as applied, leaving the
  flag column a boolean. The release manifest then failed on every start, so
  features it should have registered never were, and Marketplace stayed out of
  the sidebar — while the server, whose test is "not null", was serving
  Marketplace and Customer Accounts all along. Migration **217** converts the
  column where it is still boolean and does nothing anywhere else. It keeps
  those two features as the server already had them — on — so the sidebar now
  shows what was being served; mapping them to off would have switched off
  running portal logins on upgrade. **On such an install the manifest then
  registers the features it could never write: HxSentinel, voice input and
  voice fill, and the Database Manager appear as released.** To switch one
  off: `POST /api/v1/releases/{id}/rollback`.
- The page search (Ctrl+K) listed pages whose feature is not released; it now
  follows the same flag as the sidebar.
- A marketplace package's detail panel showed an empty description.
- **Updates on a systemd install.** `update-velaris.sh` ended by calling
  `start-velaris.sh`, which — correctly — refuses to start a second copy beside
  systemd's and exits. So the update restarted nothing, never re-applied the
  release manifest, and never rebuilt Studio (the unit builds only when the
  build is missing): new code on disk, the previous release still running, and
  the update reported as successful. The update now finishes with
  `deploy/systemd/refresh-after-update.sh`: manifest, Studio rebuilt beside the
  live copy and swapped in, units restarted. If it cannot restart them the
  result is `restart_required`, with the command, not `updated`.
- **`start-velaris.sh` could record a failed PostgreSQL migration as applied**
  (the setup and update scripts were fixed in September; this runner was
  missed). It now stops on the first failing statement, as they do.
- Creating a business calendar failed on PostgreSQL.
- Every HxMigrate pipeline run failed at stage 5; every commit answered 500
  after it had been saved; two payment lists answered 500 whenever they had a
  row; an app import with forms but no case type crashed.
- A slug-token tenant was refused its own case types.

## What changes for an existing install

**Single-tenant install: nothing.** Its administrators belong to the default
tenant, which is the platform operator, and keep everything they had.

**Multi-tenant install:**

- A non-default tenant's administrator sees and acts on **their tenant only**,
  and loses the platform-wide screens: platform updates, the Database Manager,
  process traces, regions, marketplace sources, whole-install app snapshots, and
  the untenanted security-event, push-log and GDPR-request lists.
- Compliance reports generated before this release carry no tenant and were
  install-wide; a non-default tenant's administrator no longer lists or
  downloads them.
- A role outside the new privilege lists loses actions it should never have had
  — a viewer can no longer disburse a payment or create a webhook. Roles follow
  each screen's existing navigation roles.
- A refund of an unknown id answers 404, not 400.
- A stored process whose script task is not plain assignments **fails at that
  task** with "Script refused by the safe-script check". Run the script scan
  before upgrading.

## Upgrade notes

- **Upgrade from:** v3.0.0
- **Migrations:** 206–217, verified on PostgreSQL, MySQL 8.4 and MariaDB 11.8,
  and re-runnable on each. All are additive. **206** adds three nullable columns
  for staged uploads; **207** the join-link table; **208** backfill proposals;
  **209** rail configurations; **210–211** content rollouts; **212** tenant
  ownership of case types (uniqueness relaxed from global to per-tenant, never
  tightened); **213** an owner column on eight record tables, backfilled to the
  default tenant; **214** the same inheritance columns on forms, rules, data
  models and calendars; **215** legal holds; **216** audit chain prune records; **217** (PostgreSQL
  only) repairs a flag column an early migration left as a boolean, and is a
  no-op on an install where that migration worked (see *Fixes* for what it
  changes on one where it did not).
- **Official badge for the three rail packs.** Which packages are *Official* is
  a list shipped inside the platform. An install still on v3.0.0 shows the new
  rail packs as *Community*; they become *Official* when it takes this release.
- **New settings, all off unless set:** `VELARIS_FIELD_REQUIRE_SIGNATURE`,
  `VELARIS_CASE_HXNEXUS_CHUNK_STRATEGY`, `VELARIS_CASE_HXNEXUS_RERANK` (+
  `_CANDIDATES`, `_LEXICAL_WEIGHT`), `VELARIS_CASE_PII_REDACT_TABLE_EXPORTS`,
  `VELARIS_CASE_PII_MASK_AI_EGRESS`,
  `VELARIS_CASE_RETENTION_ANONYMIZE_CASE_TEXT`. An empty or unreadable value is
  off and cannot stop a boot.
- **On a systemd install, run one command after THIS update:**
  `deploy/systemd/refresh-after-update.sh`. The update is carried out by the
  v3.0.0 script you already have, which does not know to restart the units or
  rebuild Studio. From v3.1.0 on, the update does it itself.
- **Nothing switches itself on.**
- **Tested:** case-service 6110 passed / 0 failed; Studio 287; analytics 59;
  HxMigrate 172. Two HxGraph tests fail on a box where a local embedding model
  is running — they assume there is none.
